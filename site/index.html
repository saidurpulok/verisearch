Abstract

Sampling several solutions and taking a majority vote (self-consistency) is a strong, cheap baseline for reasoning tasks. A verifier that scores each candidate should, in principle, do two things better: pick the right answer when the vote gets it wrong, and let sampling stop early once it is confident. VeriSearch tests whether either holds up under a hard cap on generated tokens, end to end on an 8 GB laptop GPU, with Qwen2.5-Math-1.5B-Instruct as the generator and a fully fine-tuned DistilRoBERTa verifier.

On 48 held-out GSM8K test problems, the verifier tied with voting. Adaptive early stopping did help, using 35% fewer generated tokens for about one point of accuracy. The verifier's 0.96 AUROC came mostly from a shortcut: almost every wrong training candidate never reached a final answer, so the verifier learned whether an answer was present, not whether it was right. Among candidates that did produce an answer, its AUROC was 0.47, no better than chance. That shortcut is the most useful finding of the pilot.

Method

  • Generator: Qwen2.5-Math-1.5B-Instruct, run locally with Transformers. Every sampling call respects the remaining token budget.
  • Verifier: DistilRoBERTa, fully fine-tuned to predict whether a candidate's final answer is correct from the question, the extracted answer and the reasoning.
  • Policies: greedy, single sample, majority vote, verifier best-of-N, and adaptive stopping whose threshold is tuned on validation only and frozen before the test run.
  • Evaluation: problem-level splits, one shared candidate pool per condition, paired bootstrap intervals, calibration metrics and a failure analysis of disagreements.

Pilot setup: 128 train / 32 validation / 48 test problems; up to four candidates per problem at temperature 0.8; 256 new tokens per trace; total caps of 256, 512 and 1024 tokens; sampling seeds 17 and 29.

  • The verifier didn't beat voting. At 1024 tokens it was one point behind; at 512 tokens it was one point ahead. Both gaps are within noise at this sample size.
  • Adaptive stopping saved tokens. It used 35.3% fewer generated tokens than scoring the full pool and lost 1.04 points of accuracy.

The verifier learned a shortcut

In the training data, 335 of the 339 wrong candidates were ones that never reached a final answer. The verifier therefore mostly learned whether an answer was present at all. A trivial rule that scores 1 when an answer is extracted and 0 otherwise reaches 95.3% accuracy and 0.963 AUROC on the test traces, matching the learned verifier.

A high verifier score here does not mean the math was checked. With only nine wrong-but-present answers in the test set, the 0.47 figure is itself imprecise, but it shows the overall AUROC is not evidence of verification.

Limitations and next steps

Limitations

  • Small test set: 48 problems, two sampling seeds and one verifier training seed, so intervals are wide.
  • One generator, one dataset and short traces of up to 256 tokens each.
  • Token savings count generated tokens only; verifier scoring, prompt prefill and model loading are excluded, so they are not wall-clock speedups.
  • Labels check the final answer, not the reasoning, and pretraining contamination is not controlled.

What comes next

  • Train the verifier on wrong answers that are present (hard negatives) to remove the shortcut.
  • Run the full 1,319-problem GSM8K test set.
  • Measure end-to-end latency, including the verifier's cost.
  • Compare against a step-level (process) verifier.

This is a small, predeclared pilot, not a full benchmark evaluation. Full caveats are in LIMITATIONS.md and the validation record in VALIDATION.md.

Run it

Requires Python 3.11–3.13, uv and an NVIDIA GPU for generation and training. CPU tests need neither a GPU nor downloaded models.

git clone https://github.com/saidurpulok/verisearch && cd verisearch
uv sync --frozen --python 3.13
export HF_HOME="$PWD/.cache/huggingface"
uv run python scripts/download_assets.py --config configs/pilot.yaml
bash scripts/run_experiment.sh configs/pilot.yaml
